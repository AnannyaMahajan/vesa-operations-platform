2. Client 
A Mid-Sized Organization Undergoing Digital Transformation 
The client is a growing organization with approximately 500 employees across multiple departments. 
As the organization has expanded, several internal business processes have continued to depend on email, 
spreadsheets, forms and messaging applications. 
The management team wants to replace these fragmented processes with a centralized internal operations platform.

3. Background 
Employees regularly need to submit requests to different departments. 
For example: 
• An employee needs access to a software application. 
• An employee needs reimbursement for a business expense. 
• An employee needs a document approved. 
• An employee needs company equipment. 
At present, these requests are handled through different channels. 
An employee may send an email to a manager, attach a document, wait for approval, forward the approval to another 
department, and then communicate with the final department through another channel. 
As the organization grows, this process is becoming increasingly difficult to manage. 
Employees often do not know: 
• Whether their request was received 
• Who is currently responsible for it 
• Whether approval is pending 
• Why a request has been delayed 
• What action is required from them 
• When the request is expected to be completed 
Managers and department staff face different problems. 
They struggle to: 
• Identify requests requiring their action 
• Track pending work 
• Prioritize urgent requests 
• Monitor overdue requests 
• Maintain a reliable history of decisions 
• Understand departmental workload 
Management also lacks a centralized view of operational performance. 
They cannot easily determine: 
• How many requests are currently open 
• Which departments have the highest workload 
• Which processes take the longest 
• How many requests are overdue 
• Where requests are getting stuck

4. Business Problem 
The organization has identified the following challenges: 
• Internal requests are distributed across email, spreadsheets and messaging applications. 
• Employees have limited visibility into request progress. 
• Managers have difficulty identifying requests requiring their approval. 
• Departments lack a centralized work queue. 
• Approval processes are inconsistent and difficult to track. 
• Important documents and supporting information are scattered across different communication channels. 
• There is no reliable audit history of important decisions and actions. 
• Overdue requests are difficult to identify. 
• Management lacks operational analytics. 
• Different business processes require different approval chains. 
• Unauthorized users must not be able to perform actions outside their responsibilities. 
5. Objective 
Design and develop a centralized Business Workflow & Operations Management Platform that allows employees to 
submit internal requests and enables the appropriate managers and departments to review, approve, process and 
complete those requests through a controlled digital workflow. 
The platform should provide a common system for: 
Request Creation  →  Review  →  Assignment  →  Approval  →  Processing  →  Completion 
The system should support different workflows for different business processes while maintaining a consistent user 
experience. 
The solution should improve: 
• Operational visibility 
• Request tracking 
• Approval management 
• Department coordination 
• Accountability 
• Process consistency 
• Security

8. Common Request Lifecycle 
Although each business process has its own workflow, all requests should follow a controlled lifecycle. 
A typical lifecycle is: 
Submitted  →  Under Review  →  Approval Pending  →  Approved / Rejected  →  Processing  →  Completed 
Students may introduce additional states where required. 
For example: Changes Requested or Cancelled. 
However, every status must have a clearly defined purpose. 
Students must determine: 
• Who can change a status 
• Under what conditions it can change 
• Which status can come next 
• What happens when a request is rejected 
• What happens when additional information is required

9. Request Management 
Every request should have a unique identifier. 
Example: REQ-2026-00124 
The request details page should provide a complete view of the request, including: 
• Request information 
• Current status 
• Current owner/assignee 
• Priority 
• Submitted date 
• Required date 
• SLA status 
• Comments 
• Attachments 
• Approval decisions 
• Activity history 
The user should be able to understand the current state of a request without searching through emails or messages. 
10. Approval & Action Management 
The platform must provide role-specific actions. 
Depending on the request and current workflow stage, a user may be allowed to: 
• Approve 
• Reject 
• Request Changes 
• Assign 
• Reassign 
• Start Processing 
• Update Progress 
• Complete 
• Add Comment 
The backend must enforce these permissions. 
Hiding a button on the frontend is not considered authorization. 
For example, even if an employee cannot see an “Approve” button, the backend must still reject an unauthorized 
approval request sent directly to the API.

11. Comments & Clarification 
Users should be able to communicate within a request. 
For example: 
Finance Officer: Please upload the original receipt. 
The employee can then provide the required document. 
The system should maintain this communication as part of the request history. 
Students should consider: 
• Who can comment? 
• Who can view comments? 
• When can comments be added? 
• Can comments be edited? 
• Should important actions require comments? 
These decisions should be documented as assumptions.

13. SLA & Overdue Requests 
The organization wants to monitor how quickly requests are processed. 
Each request type should have a target processing period. 
Request Type Target 
Software Access 24 hours 
Expense Reimbursement 48 hours 
Document Approval 72 hours 
Equipment Request 72 hours 
The system should identify requests that are: 
• Within SLA 
• Approaching SLA 
• Overdue 
• Completed within SLA 
• Completed after SLA 
Students should calculate SLA status using actual request timestamps rather than storing a manually entered label.

17. Audit Trail 
The system must maintain an audit history for important actions. 
Example: 
REQ-2026-00124

11:07 AM — Assigned to IT Administrator

The audit trail should answer: 
• Who performed the action? 
• What action was performed? 
• Which request was affected? 
• When did it happen? 
• What was the relevant decision or status?

18. Authentication & Authorization 
The application must implement secure authentication. 
At minimum: 
• User registration or administrator-created accounts 
• Login 
• Secure password handling 
• Protected routes 
• Session/JWT-based authentication 
• Logout 
The system must implement role-based authorization. 
For example, an Employee should not be able to: 
• Access another employee's private requests 
• Approve requests 
• Modify system configuration 
• Access administrative analytics 
A Manager should not automatically receive administrative permissions. 
A user should only be able to perform actions appropriate to their role and the current workflow stage. 
19. Business Rules & Constraints 
The following constraints are mandatory considerations: 
• An employee cannot approve their own request. 
• A request cannot skip mandatory approval stages. 
• Only authorized users can perform workflow actions. 
• Rejected requests must contain a reason. 
• Requests requiring changes must return to an appropriate stage. 
• A request cannot be marked completed without completing its required processing stage. 
• Users must not access requests outside their authorization scope. 
• Supporting documents must only be accessible to authorized users. 
• SLA status must be calculated from relevant timestamps. 
• Important workflow actions must be recorded in the audit trail. 
• The system must prevent invalid status transitions. 
• Deleting important business records should not destroy their historical accountability. 
• Backend authorization must be enforced independently of frontend UI restrictions.

• How will SLA deadlines be calculated? 
• What happens when a request becomes overdue? 
• How will the system handle a user changing departments? 
• How will you ensure users cannot access another user's confidential documents? 
• What happens if two users attempt to update the same request?

30. Final Project Mindset 
Project 3 is designed to simulate the type of problem a software services team may receive from an organizational 
client. 
The client does not tell you: 
• Which database tables to create 
• Which APIs to write 
• Which React components to build 
• How to structure your folders 
• Which libraries to use 
• Exactly how your UI should look 
Instead, the client gives you a business problem, stakeholders, processes, rules and constraints. 
Your job is to convert that information into a reliable software solution. 
Don't build what you think looks impressive. Build what solves the client's problem. 
This is the final project of the VESA Skill Development Program. 
Build the system like an engineer. Document it like a professional. Defend your decisions like a software developer.
